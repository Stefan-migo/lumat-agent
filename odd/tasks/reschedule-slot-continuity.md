# Reschedule slot continuity

The reschedule node refuses the customer's own words: it only reads a menu number, so a day the
handoff gate already accepted ends in the single clarification and an immediate escalation.
Branch: `odd/reschedule-slot-continuity` · Runner: `scripts/test.sh` · Worktree: `../lumat-agent-odd-reschedule-slot-continuity`.

## Specs

- **S1** — User, request verbatim: «ok chat necesito que eentres al vps nuevamente para revisar el ultimo caso. este es un bug que me paso antes. Al intentar reagendar una visita técnica que ya está agendada, el chatbot entrega posibles días de visitas técnicas como alternativa. Y cuando le digo que no me sirve ese día, que necesito otro día, no lo reconoce. No es capaz de volver a dar la alternativa correcta.»
- **S2** — User, decision: «Sí, worktree ODD y fix completo» and, for a relative week without a day: «Mantener día y franja ya capturados — Si dijo sábado 10:30, ofrecer el sábado de la semana siguiente en esa franja; si no hay, avanzar». Investigation, review and the fix in an ODD worktree are authorized; production, push, PR, merge and deploy remain separate decisions.
- **S3** — Measured production evidence (read-only, release `v2026.11.21`, 2026-11-27). Conversation 48, 26/11 23:01–23:05 UTC, case 40 `escalado` with `handoff:manage_unclear`: 1. Customer selects visit 2 of a menu. 2. Bot offers three Friday slots. 3. Customer: «Puede ser para la próxima semana? Lunes quizás en la mañana?» 4. Bot: «No pude identificar un único horario. Responde con el número de una opción.» 5. Customer: «No me sirve el horario que me diste, necesito reagendar para la próxima semana» 6. Bot: «Un asesor revisará tu caso y te contactará a la brevedad.» The same sequence occurred on 19/11 in conversation 42 with «No, necesito reagendarla para una semana más. O sea el sábado siguiente».
- **S4** — Root cause to fix, confirmed against the deployed image: `handoff_gate._answers_manage_offer` accepts the turn through `booking.is_offer_answer` (selection, `resolve_window`, or a request for more options), and then `manage.manage` only tries `booking._resolve` against the three offered slots. A preference that resolves (`resolve_window("Puede ser para la próxima semana? Lunes quizás en la mañana?")` → `la mañana del lunes 30/11`) is discarded, `_invalid` spends `MAX_INVALID_REPLIES = 1`, and the next turn escalates. The gate and the node must agree.
- **S5** — Required outcomes: 1. A reply that names a day and/or franja rebuilds the reschedule offer from the real agenda for that window. 2. A reply that names a relative week without a day (`próxima semana`, `la semana que viene`, `la otra semana`, `en una semana`) rebuilds from the reference day and franja the conversation already has, seven days forward. 3. A reply that rejects the menu without naming anything (`no me sirve`, `ninguno me sirve`, `otras opciones`, `otro día`) offers the next available options forward instead of asking for a number again. 4. A reply that answers none of the above keeps exactly one clarification and then hands off, as today. 5. No rebuild reprints the identical menu. 6. Nothing is rescheduled and the original appointment is untouched until the customer selects a slot.
- **S6** — Constraints: reuse the existing machinery (`resolve_window`, `slots_for_window`, `_requests_more_slots`, `is_offer_answer`); add no reply-text key and no parallel scheduler; cancellation, the select phase, booking and capture keep their current behavior; no production access, deployment, push, PR or merge without separate authorization.
- **S7** — Regression protection: cover the three continuity paths through `run_conversation` with a real isolated PostgreSQL, asserting the reply text, the persisted `_manage_offer`, and that the appointment and its history stay unchanged; keep the genuine-ambiguity escalation and the `no`/`no gracias`/`mejor no` path green; re-state the superado expectation in `test_reschedule_ambiguous_slot_reasks_once_then_hands_off`; run `quick` and the focused suite during implementation and `full` at feature closure.

## Design decisions

- **D1** — Resolution order inside the `slots` phase, after the existing `no`/`mejor no` keep-visit path: menu selection → `resolve_window` → relative-week reference window → request for more options → the existing invalid budget. Each step only runs when the previous one could not serve the turn.
- **D2** — Reference for a relative week: the appointment being moved (its local date plus seven days, its franja from `local_start`), overridden by the captured `availability` window when capture stored one. That is the owner's decision in S2, and it is the only reference available when capture never ran for a reschedule.
- **D3** — A rebuild that produces the same slot list as the offer on screen does not reprint it: it falls through to the next resolution step. Reprinting an identical menu is the loop the booking node already guards against.
- **D4** — Rebuild rounds are capped (`MAX_REBUILD_ROUNDS`) so a customer can move forward several times but not endlessly; when the cap is reached the node hands off. Rebuilding for a valid preference never spends the invalid budget, and the invalid budget keeps its current single clarification.
- **D5** — Replies reuse the existing catalog keys (`manage_slots_offer`, `booking_window_unavailable` for a widened offer, `manage_slots_unclear`). No new key, so `tests/unit/test_reply_texts.py` stays intact.
- **D6** — `_new_reschedule_offer` gains an explicit `window`, a `rounds` counter and an `unchanged_against` offer; the last one is what lets D3 answer "this rebuild would reprint the menu" without a second comparison helper. Appointment identity, the ownership/status guards and the final `scheduling.reschedule` call are untouched.
