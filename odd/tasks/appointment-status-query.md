# Appointment status query

The bot has no way to answer a question about the visit the customer already holds: the turn is
claimed either by the free-agenda preview or by the capture questionnaire, so "¿qué técnico va?"
receives free hours and "tengo una hora agendada" receives "todavía no queda agendada".
Branch: `odd/appointment-status-query` · Runner: `scripts/test.sh` · Worktree: `../lumat-agent-odd-appointment-status-query`.

## Specs

- **S1** — User, request verbatim: «hey chat necesito que entres al vps solo lectura y revises la ultima conversacion. donde el cliente consulta por su visita agendada. pero al parecer el chatbot no tiene como responder sobre las visitas ya agendadas, fecha, hora, tecnico? podemos implementar esa logica? dame un overview antes de continuar»
- **S2** — User, decisions verbatim: «1. si» (nombrar al técnico siempre, no sólo el día de la visita), «2. si nombrar todas» (listar todas las visitas próximas, no sólo la más cercana) and «3. el texto.» (técnico sin asignar responde un texto; no deriva a una persona). Implementation in an ODD worktree is authorized; push, PR, merge and deploy remain separate decisions.
- **S3** — Measured production evidence (read-only on the VPS, 2026-11-27). Conversation 50, `+5492972542298`, turns 03:51:40 and 03:52:15 UTC: 1. «Tengo una visita para el lunes, puedes confirmarme que técnico va?» → «El lunes 30 tengo estas horas libres: a las 09:00, 09:30 y 10:00. Si te sirve alguna, te tomo los datos y te reservo.» 2. «Tengo una hora agendada para el lunes» → «Anoté lunes como preferencia; la visita la confirmamos al coordinar, todavía no queda agendada. Cuéntame qué pasa con el equipo: ¿no enciende, no calienta o muestra algún código de error?» The appointment that answers both turns exists and is untouched: `appointments` id 24, `customer_id` 2, `status` `booked`, `local_start` `2026-11-30 14:00:00`, `timezone` `America/Santiago`, `technician_id` 4 (`Max Escanilla`), `service` `Visita técnica`; it is the visit conversation 49 rescheduled 76 seconds earlier (03:39:16 UTC, «Tu visita quedó reagendada para el Lunes 30/11 a las 14:00.»). `conversation_events` for 50 records `classified intent:consulta`, `kb_retrieved chunks:5` for the first turn and no retrieval event for the second, which is the evidence that the second turn was answered by `capture` and not by the model.
- **S4** — Root cause to fix, confirmed against the deployed image: no path in the pipeline reads the customer's own appointments to answer a question. (a) Turn 1: `respond` calls `configuration_reply` (`respond.py:890`), whose order is duration → coverage → availability → hours (`configured_answers.py:543`); `availability_reply` claims any turn that names a window and asks something, so the question about the booked visit is answered with free slots. (b) Turn 2: `orchestrate` computes `day_selection` (`orchestrate.py:332`) and routes to `capture`, which stores «lunes» as a preference and answers with `capture_availability_ack` (`settings.py:259`) — the sentence that denies the appointment. (c) Even on the model path the data is incomplete: `<booking>` carries service, label and status (`state.py:345`, `respond.md`) but never the technician, and `prompts.py:64-66` forbids confirming an unconfirmed visit without forbidding the denial of a real one. (d) `manage` only knows cancel and reschedule, and only behind an explicit change verb (`orchestrate.py:132-159`); an informational question has no owner.
- **S5** — Required outcomes: 1. A turn that asks about the visit the customer already holds is answered from the appointment rows themselves: date and hour in the customer's local time, the service, and the technician (S2.1). 2. Every upcoming `booked` visit is named — up to three, numbered — not only the nearest one (S2.2). 3. An appointment with no technician assigned answers with a text and never derives to a person (S2.3). 4. A customer with no upcoming visit reads that fact, not free hours. 5. Such a turn is never answered with free-agenda slots, never answered as a capture field, and never says a booked visit is not booked. 6. An explicit request to change or cancel keeps reaching `manage` unchanged.
- **S6** — Constraints: no model call and no new scheduler — the answer is deterministic and reads the same rows `manage` and `case_ficha` read; reuse `when_label`, the technician name resolution and the `reply.texts` catalogue; every new customer-facing string is an owner-editable key with a default that the code ships; no schema change, no migration, no production access, deployment, push, PR or merge.
- **S7** — Regression protection: keep availability questions («¿tienen hora el lunes?», «¿atienden el sábado?»), the configured-hours answer, cancellation, rescheduling, booking and capture green; add the exact production turns as RED cases before the fix; run `quick` during implementation, the focused DB suites and `full` at feature closure; run one differential check for the shared `configuration_reply` precedence against the baseline commit.

## Design decisions

- **D1** — The answer is a new deterministic responder, `appointment_status_reply`, placed in `configuration_reply` **before** `availability_reply` and after duration and coverage, so a question that also asks how long the work lasts keeps its own answer. It reads `booked` appointments with `starts_at > now`, ordered ascending, limit 3.
- **D2** — The trigger is a narrow phrase set over folded text (`mi visita`, `tengo una/hora agendada`, `visita agendada`, `qué técnico`, `quién va`, `a qué hora viene`, `confirmar` next to a visit noun), in a new shared module `app/chat/visit_questions.py` that holds `asks_about_booked_visit` and the moved `asks_for_change`. Both `orchestrate` and `configured_answers` read the same predicates, so the router and the responder cannot disagree.
- **D3** — Routing: `_dispatch` gains a `booked_visit_question` flag and returns `respond` for it ahead of every `reagendar_visita`/`day_selection` branch, and `day_selection` is computed with the same predicate, so the turn reaches the responder instead of the questionnaire. A `change_request` turn is excluded from the flag and keeps its `manage` path.
- **D4** — `<booking>` gains the technician (and `por asignar` when there is none) in `state.from_db` and in the prompt block, and `prompts.py` gains the rule that a visit `<booking>` records exists: it is named, never denied, and never re-offered as if unscheduled.
- **D5** — Texts: `appointment_status_one`, `appointment_status_many`, `appointment_status_none`, `appointment_line` and `appointment_technician_unassigned` in `REPLY_TEXT_DEFAULTS` and `REPLY_TEXT_SLOTS`, with their defaults shipped by the code; the numbered line mirrors `manage_select`'s shape.
- **D6** — Technician naming is extracted to one helper reused by booking, the status answer and the prompt context, so the three cannot drift apart; the existing `TEAM_FALLBACK` behaviour for a nameless technician stays as it is.
